# Deep Crew Grilling

## 目的

把交付内容中的高影响歧义在当前对话里变清晰，使调用方能够安全生成 REQ、SPEC、IMPLEMENTATION 或 ACCEPTANCE 内容。它是节点内部的辅助流程，不是独立节点，也不是 Issue 时间线中的事件类型。

本技能不自行调用 `dc-issue-intake`。由 `dc-context-loop` 按读取门禁完成必要的完整 intake，并把当前 Agent 会话中的 Issue context 交给本技能复用；本技能只读取仓库、代码或运行环境查明可验证事实。不要让用户回答 Agent 自己能查到的问题，也不要基于陈旧缓存继续讨论。若当前会话没有有效 Issue context，应返回总协调器补做 intake，而不是自行读取或猜测。

## 启动尺度

先判断歧义是否会改变当前动作的结果：

| 情况 | 动作 |
|---|---|
| 内容已经足够明确 | 不启动，直接推进目标节点 |
| 只影响措辞、排版、命名或低风险实现偏好 | 采用项目约定，不追问 |
| 歧义低风险、可逆且不会改变验收结果 | 明确非阻塞假设后继续 |
| 歧义会改变业务结果、范围、失败行为、验收裁决、公开接口、数据兼容或不可逆操作 | 启动讨论 |
| 问题只影响未来优化 | 延期，不阻塞当前交付 |

讨论目标是“当前动作可以安全执行”，不是把所有可能问题都问完。

## 对话算法

1. 确认当前要生成或修改的目标内容及当前动作。
2. 从 Issue 全部评论和本地环境中区分已知事实、已确认决策和真正的未决问题。
3. 先自行查明环境事实；只有必须由负责人决定且会改变当前结果的问题才询问用户。
4. 一次提出 1-3 个当前可回答、互不依赖的高影响问题，说明每个问题为什么影响当前动作，并在有依据时给出推荐。
5. 根据用户回答更新当前共享理解。依赖上游答案的问题等答案明确后再问，不预先铺开整棵树。
6. 一旦当前动作可以安全执行，立即停止追问；把剩余内容分为非阻塞假设或延期问题。
7. 用简短摘要向用户确认将写入目标节点的内容。用户已明确表达且没有多义性时，不为了形式重复确认。
8. 把确认结果返回调用方，由调用方直接生成对应的 REQ、SPEC、IMPLEMENTATION 或 ACCEPTANCE 事件。

问题不要求稳定编号。需要在单次较长回复中帮助用户对应多个问题时，可以使用临时序号；这些序号只服务当前对话。

## 收束判断

满足以下条件就收束：

- 当前动作所需的高影响问题已有答案、明确不适用，或用户授权采用已说明的建议；
- 关键范围、责任、可观察结果和风险没有隐藏的阻塞假设；
- 剩余问题不会改变当前交付结果，已作为非阻塞假设或延期问题说明；
- 调用方已经获得足以生成目标节点结构化内容的共享理解。

如果用户暂未回答关键问题，暂停目标节点的写入并说明缺少的决策。不要发布“等待回答”的讨论评论，也不要把推荐答案当成用户答案。

## 不同目标的关注点

| 目标 | 重点澄清 | 避免询问 |
|---|---|---|
| REQ | 用户、业务结果、范围、失败行为、依赖、约束 | 代码目录、框架、测试库 |
| SPEC | 前置条件、动作、可观察结果、覆盖关系、裁决规则 | 纯格式偏好 |
| IMPLEMENTATION | 必须由负责人决定的方案取舍、兼容性、风险、不可逆变更 | 能从代码查到的实现事实 |
| ACCEPTANCE | 仅在验收定义、证据要求或阻塞归属不清且导致验收无法安全继续时澄清 | 执行验证、审查 RUN/ART、裁决 AST、判断是否通过，或脱离证据询问“要不要算通过” |

完整的内部设计树判断见 `references/design-tree.md`。设计树只帮助 Agent 决定“现在问什么、何时收”，不产生持久化结构。

## 输出给调用方

讨论结束后只返回当前目标所需的信息：

- 已确认内容：可以写入目标节点的事实和决策；
- 非阻塞假设：当前采用但不妨碍推进的假设；
- 延期问题：不属于当前动作的问题；
- 阻塞问题：仅在仍无法推进时列出；
- 目标动作：调用方下一步应生成或修改哪个内容。

若某个业务决策需要长期保留，把它转换成目标节点的结构化字段、发布原因或影响信息。

## 与 Context Loop 的关系

`dc-context-loop` 负责按读取门禁完整读取 Issue、选择当前内容节点、调用本技能并在讨论结束后发布目标事件。本技能只负责复用当前会话中的 Issue context、查明本地事实、必要追问和收束，不调用 Issue intake，也不读取或写入任何“讨论状态”。
