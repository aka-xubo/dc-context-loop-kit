# REQ 需求追问

REQ 确认前，使用分轮次的需求追问把业务结果、边界和验收前提问清楚。该过程借鉴 design-tree / grilling 方法，但属于 `delivery-proof` 的 REQ 分析步骤，不是新的技能、状态或门禁。

## 适用时机

- 新建 REQ，尤其是一句话需求或来源材料不完整时；
- 当前 REQ 尚未明确，且业务结果、范围或约束仍有多种合理解释；
- `dc-requirement-slicing` 判断需要重新整理当前需求时。

纯实现变化不重新追问；需要调整业务目标、范围或结果时重新整理当前 REQ。纯探索、技术调研和临时排障不进入 Delivery Proof。

## 先查事实，再问决策

在提问前读取当前 Issue/来源材料、现有 REQ、相关场景和项目约束。Agent 自己能从环境查到的事实不得拿来询问用户；只有业务负责人需要作出的选择才进入问题清单。

事实和决策分开记录：

- 事实：来源、当前代码或环境中已经存在，可引用并继续分析；
- 决策：会改变业务责任、用户可观察结果、范围、异常行为、依赖或验收方式，需要用户选择。

## 分轮次工作

1. 生成当前 frontier：只列出前置事实已经明确、现在可以回答的问题。
2. 一轮一次问完当前 frontier；问题编号，说明影响，并给出推荐答案。不要把依赖尚未确定的问题提前混入本轮。
3. 等待用户回答后，基于回答重新计算 frontier，再进入下一轮。
4. 用户没有回答关键问题时不要发布 REQ 快照，不能猜测或直接进入 SCN/矩阵。

问题优先覆盖：

- 谁在什么前置条件下完成什么业务动作；
- 成功结果和关键失败/拒绝结果是什么；
- 纳入和排除哪些业务范围；
- 权限、数据边界、外部依赖和保护不变量；
- 结果通过哪个用户或系统交付面被观察。

不要为了选择框架、目录、测试库、接口路径或测试工具而追问；这些属于实现计划或验证环境。

## 收敛与确认

当没有未决的业务决策，生成一份完整的当前 REQ 快照，确保 `statement`、`business_value`、`scope`、`dependencies` 和 `source_refs` 能反映共同理解。未解决的问题留在当前对话中，不向需求 YAML 添加未定义字段。

最后明确展示：REQ 摘要、纳入/排除范围、依赖、仍存在的风险和下一步门禁。只有用户明确确认后，才能写入既有 `confirmation` 并将 REQ 置为 `CONFIRMED`；Agent 不得代替用户确认。

REQ 确认后，按 `dc-acceptance-design` 继续设计场景，再设计 CHK/AST 矩阵。追问过程本身不产生 SCN、CHK、RUN 或 ART。
